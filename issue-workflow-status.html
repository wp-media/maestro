Known open issues in the reference 8

  • IMPL_SCHEMA in commands/orchestrator/workflows/implementation.js (line 46) still enumerates dod_layer1.overall as ['PASS','WARN'] — missing 'FAIL'. The F1 fix landed in the agent .md files, the orchestrator contract (L247), and dod.md, but NOT in the Workflow schema. A legitimate dod_layer1.overall:'FAIL' escalation return (which the agents are now told to emit after 3 failed self-corrections) would be rejected by the Workflow's StructuredOutput schema validator. This is the single most concrete remaining contract bug from the audit (Fix #1).
  • Audit D1 NOT applied: the 16-20-line 'Config loading (always first)' block is still duplicated verbatim across all 9 core agent files, including dead variables never referenced outside the table (e.g. SLUG/DISPLAY_NAME/EDITIONS/FRONTEND_SKILL/REST_NS in challenger, ticket-writer, release-agent, lead-reviewer). The orchestrator now injects a reduced config set per agent, so the per-file blocks are redundant boilerplate parsed on every invocation (~150 recoverable lines). The recommended fix (drop the per-agent block, inject only used vars) is not done.
  • Audit D2 NOT applied: backend-agent and frontend-agent remain near-identical twins (shared re-invocation block, DOD-L1 escalation paragraph, commit/no-push/trailer rules all duplicated). Not merged into a shared contract or parameterized single agent — policy changes must still be made in two places, and the audit already observed drift between them.
  • Audit F7 NOT fully resolved: three severity vocabularies still coexist feeding the ticket-writer NTH dispatch — challenger MoSCoW (MUST/SHOULD/COULD/NICE_TO_HAVE), qa-engineer MoSCoW, but lead-reviewer uses CRITICAL/HIGH/MEDIUM/LOW criticality on blockers plus a separate SHOULD/COULD/NICE_TO_HAVE on nice_to_haves. No single canonical NTH severity scale (Fix #9 'adopt MoSCoW as the canonical NTH severity' only partially done).
  • Audit hardening Recommendation 1 NOT applied: orchestrator L373 is still the bare 'Read grooming JSON.' rather than the recommended 'Read the grooming agent's inline return JSON (do NOT read spec.md).' — leaving a future model the temptation to cat the spec.
  • Audit hardening Recommendation 2 NOT applied: the inline-only invariant ('the orchestrator routes ONLY on inline agent return JSON and Workflow return values — it never reads an agent's *.json/*.md output off disk') is not codified in the orchestrator's Core principles, so /contract-check and /pipeline-health cannot mechanically enforce it.
  • Per-file verbosity trims (audit D3 / Fix #12) NOT applied: qa-engineer still duplicates the 'never re-run PHPCS/PHPStan/Codacy' prohibition across Strategy C and Step 4; grooming-agent still states PR-split rules in both Step 4 and Step 4b; challenger still carries 3 separate prose output templates; e2e-qa-tester still has the 'Known limitations' roadmap notes. Roughly 95+ lines the audit flagged as trimmable remain.
  • Version not tagged: plugin.json declares 0.5.2 but no git tag v0.5.2 exists (HEAD is v0.5.1-10-g138f361). The 0.5.2 changes — including all the above-applied audit fixes — are committed and version-bumped but unreleased/untagged, so 'declared 0.5.2' describes work ahead of the last cut release.

⬇ Behind Maestro 4

  • Auto-resolve addressed PR review threads (orchestrator Step 8)
    Maestro posts a 'Fixed in <sha>' reply and runs the GraphQL resolveReviewThread mutation on each addressed thread after every fix push; imagify's orchestrator has no such step, so after fix loops the lead-reviewer's inline threads stay open on the PR and a human must resolve them manually.   • smoke_tests[].result enum widened to PASS|FAIL|N/A (audit C13 / Maestro F4)
    imagify's smoke_tests[].result is still narrower than its sibling criteria_results enum, so a smoke check that cannot run (boot failure) gets force-fit to FAIL rather than N/A.   • Per-check status enum unified to PASS|WARN|FAIL|N/A across L1/L2/orchestrator (audit C17 / Maestro F11)

  • StructuredOutput return contract (+ epilogue)
    Returns are prose+fenced-JSON parsed from agent output; no schema-validated StructuredOutput path. Higher risk of malformed/missing returns and silent routing on the wrong field — the entire reliability track of Maestro 0.5.x is absent.
  • Lead-reviewer Copilot-parity wave (cross-file/Hyrum step, confidence filter, ```suggestion blocks, named security/perf checklists, grouping, severity tags, inline-diff-only, comment dedup)
    Reviews are diff+spec+standards only with no repo-wide symbol-impact analysis and no observable-behavior (Hyrum) check, so cross-file breakage and behavior-contract changes slip through; review comments can be noisy, duplicated on re-invocation, and lack one-click suggestions. This is the largest single quality gap.
  • DOD-L1 FAIL escalation value
    L1 overall is hard-capped at PASS|WARN with an explicit 'never FAIL' instruction, so a genuinely failing self-check has no typed escalation return — the agent either loops on self-correction or stops in prose, with no clean FAIL signal for the orchestrator.
  • Anti-scope-creep gate (4-point) before implementation
    Nothing checks that implementation scope maps 1:1 to acceptance criteria or that complexity stays within the groomed effort before code is written — scope creep can reach the PR before any review catches it.
  • Comment dedup via HTML markers (grooming, lead-review, QA) + review-thread auto-resolution
    Re-invocations (up to 3 for lead-review and QA) re-post comments instead of PATCHing in place, and addressed review threads are never auto-resolved — PRs accumulate duplicate/stale comments across loops.
  • Intent-read escalation calibration + named loop counters + WIP timeouts
    No high-autonomy/standard/high-oversight adaptation to the requester's intent, no persistent named loop registers, and no 'reassign after 3 same-error failures' WIP layer — escalation is a fixed list, less adaptive and less robust to thrashing.
  • Parallelism (git-worktree isolation + Workflow scripts)
    Backend, frontend, and all quality gates run strictly sequentially; no implementation.js/quality-gates.js. Loses Maestro's ~40-50% cycle-time reduction on both-domain work.
  • Externalized config (maestro.json) + no-hardcoded-strings rule
    Repo slug (incl. a STALE 'wp-media/backwpup'), temp paths, composer commands, and localhost URL are hardcoded across agents; not project-agnostic and drift-prone. (This is exactly what the migration fixes.)
  • Adaptive grooming complexity_signal + model routing + PR-splitting + markdown-escaping rules
    Grooming runs at a fixed model with no reasoning-depth adaptation, never produces a vertical-slice plan for L/XL work, and lacks GitHub markdown-escaping rules — large tickets aren't decomposed and posted comments risk rendering bugs.
  • Inline docs-skill run on public-API change + standalone /dod, /docs, /e2e commands
    Doc updates for new hooks/REST/AJAX/config are not handled inline, and there are no reusable slash-command entry points for DOD/docs/E2E outside the full pipeline.
  • ticket-writer agent (NTH follow-up creation)
    The orchestrator dispatches NTH items to a 'ticket-agent' that has NO file in the repo — a dangling reference, so non-blocking follow-up tickets cannot actually be created today.
  • Single canonical MoSCoW NTH severity scale
    lead-reviewer uses CRITICAL/HIGH/MEDIUM/LOW while challenger/QA use MoSCoW — two vocabularies feed NTH dispatch, same unresolved split as Maestro itself (so updating only narrows, not closes, this one).
  • Centrally-gated AI-transparency (trailer verification/amend, CURRENT_MODEL threading, [!NOTE] PR first line)
    Attribution is by-convention with a hardcoded model string and no verify/amend or pre-finalize gate — a missing Co-Authored-By trailer or notice would not be caught.

⬆ Ahead of / diverges from Maestro 3

  • Dedicated ci-agent that enumerates checks from workflow YAML
    ci-agent.md reads .github/workflows/*.yml to report WHICH checks will run before polling, then monitors gh pr checks every 60s to ALL_PASS/FAILURE/TIMEOUT@20min with targeted --log-failed excerpts and root-cause hints. Maestro has no standalone CI agent — it folds CI monitoring into the orchestrator. As a discrete, read-only, reusable CI observer this is a capability Maestro lacks (though it is also a maintenance surface the Maestro design deliberately avoids).
  • Typed free_pro_impact enum as a first-class routing signal
    grooming returns NONE|FREE_ONLY|PRO_ONLY|BOTH|BOUNDARY_CHANGE and BOUNDARY_CHANGE unconditionally triggers the challenger. Maestro's editions-awareness is a boolean-ish per-file annotation + scope partition; this project encodes edition impact as an explicit graded signal that directly drives the adversarial-review gate — a sharper trigger than Maestro currently has (Maestro is ahead on the scope-partitioning half, behind on the trigger half).
  • free_pro_impact surfaced in the run-log decisions strip
    The HTML log's decisions strip has a dedicated 'FREE/PRO impact' column and the ROUTING DECISION event template calls out when free_pro_impact drove the decision — edition impact is a visible, audited routing dimension, which Maestro's generic log does not special-case.
